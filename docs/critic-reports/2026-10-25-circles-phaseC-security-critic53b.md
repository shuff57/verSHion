## Blockers (new class)

### B1. Email per-address cap is defeated by dots and provider aliases: one mailbox can be mail-bombed, and the site-wide hourly budget exhausted (D5 "nobody can be mail-bombed")
- `server/worker/src/pool/circlemail.ts:39` `emailCapKey` only lower-cases and strips a `+tag`. It does not fold dots in a Gmail local part or the `googlemail.com` alias, so `v.i.c.t.i.m@gmail.com`, `vic.tim@gmail.com`, `victim@googlemail.com` and `+victim@gmail.com` each get their own HMAC row and their own 3 mails/day.
- Repro (e1.test.ts): one inviter, 16 variants of one Gmail address: `victim@gmail.com`, `vic.tim@`, `v.i.c.t.i.m@`, `victim@googlemail.com`, `+victim@`, `vic.tim+z@` were each mailed (the plain, `+tag` and case forms are suppressed as designed). Repro (e3.test.ts): 5 approved accounts, 2 circles each, 20 dotted variants of one name: 100 of 100 accepted, 100 mails to one Gmail mailbox (cap says 3/day), then a legitimate teacher's invite in the same hour is `503 busy` (`circle_email_hourly` = 100 spent). One account alone can send 20 a day to one mailbox.
- Severity: medium-high. Needs approved accounts (1 for 20 mails, 5 for the hour DoS), each mail carries an attacker-chosen circle name (see V1).
- Fix: fold the local part per provider (strip dots for gmail.com/googlemail.com, map googlemail to gmail), and/or add a second cap keyed on the domain (e.g. n mails an hour to one domain) and a per-inviter distinct-recipient-domain cap.

### B2. Hidden-key bank: the viewers' served (stripped) form is never checked against student-data or copyright blocks, so a block is evaded exactly where the viewers read
- `server/worker/src/pool/circlesend.ts:667` and `:1183` call `privacyScan` with the FULL form's hashes only (`prep.matchHashes` / `mh`); the stripped form's hashes (`pairs`, `prep.stripped.matchHashes`, line 658) are used only for D13 records. `patchHideKey` (`circles.ts:1396-1462`) runs no block check at all when it turns the setting on. The public path holds on both forms.
- Repro c1.test.ts (a public hide_key item with choice labels "A. " is taken down; the block holds the unlabelled served form): public re-upload (labelled, `hide_key` true) is HELD (`item_holds` blocklist). Circle send of the same labelled text with `hide_key:true, labels:[strip]` is `201 held:false withheld:false`, while the unlabelled text is held. Repro c2.test.ts: a clean labelled send (not held), then `PATCH {hide_key:true, labels:[strip], order_acks}` returns 200; a viewer then reads exactly the taken-down text (`["Mitochondrion","Ribosome",...]`) with no hold and no `admin_flags` row. Same code path for `privacy_blocks` (confirmed student data).
- Why it is a class, not a trick: it needs no edit of the text (a deliberate typo evades an exact-hash block everywhere); it is the "stored form is not the served form" gap that the README says phase C closes for D13 only. A teacher re-uploading the genuine original into a hide-key circle gets it served to viewers unflagged while the public path would hold it.
- Severity: medium. Fix: add `pairs[*][1]` (served hashes) to the `keys` passed to `privacyScan`/`COPYRIGHT_SQL`/`PRIVACY_SQL`, in send, rollback (the target's stripped form via its `strip_opts`) and `patchHideKey` (hold plus withhold the head when the served form matches).

## Variants and limits

- V1. Platform-sent phishing text: the only free text in the mail is the circle name (`poolmail.ts` `circleInviteText`, cleanText allows URLs, quotes, 80 chars). e2: a circle named `Account suspended - verify at https://evil.example now` is mailed from the service's address as `the circle "Account suspended ... now" on verSHion`. Mitigation: refuse URL-like and quote characters in names used in mail, or omit the name.
- V2. Targeted silencing, same answer: anyone with 3 invites a day to an address makes every later invite to it (any circle, any inviter) return the same `202`, listed `active`, but never mailed (e2: legit invite `202`, mailed 0). Inviters cannot tell; no "was this sent" signal. Also silent: valid-by-circlemail but rejected-by-poolmail addresses (`EMAIL` in `poolmail.ts` needs a letters-only TLD, so `xn--` TLDs and `1.2.3.4` are counted, answered 202 and never mailed), a provider failure (only `console.error`), and `a..b@x.com`-style local parts (accepted by `EMAIL_RE`).
- V3. Hourly budget (`circle_email_hourly` 100) is a shared DoS target: 5 approved accounts spend it in one hour (e3). Requests that later fail the code write give the slot back; invalid addresses still spend it.
- V4. `PATCH ...banks/:bid {hide_key}` is publish-sized work with no daily metric (only the generic 300 requests / 5 min per account). p1: 12 parallel strips of a 1,000-question (456 KB) bank all return 200, ~190 ms CPU each. p2: 200 on/off toggles give 200 permanent `pool_audit` rows (no-delete trigger) and the first activity page (50 lines) is all `hide_key_changed`, burying real events. Same class as the existing unmetered `license` PATCH (p3: 100 rows), but heavier. Suggest a daily metric (e.g. `circle_hide_changes`) and no audit line for a no-op.
- V5. Viewer strip reads: `circle_hidden_reads` 100/day each ~140 ms for a 456 KB bank (h4); `HEAVY_CONCURRENCY` 1 and `OPEN_READS_PER_ACCOUNT_ADDRESS` 2 bound one account, but many viewer accounts sharing a circle (50 members) can keep the isolate busy; reads do not interleave with CPU-bound strips (the slot guards memory, not CPU).
- V6. Stale ETag: the head JSON that the ETag hashes does not include `strip_opts`, so re-recording decisions (labels keep to strip) changes the served bytes without changing the ETag; a viewer revalidating with `If-None-Match` keeps the old copy (also a 304/HEAD answers 200/304 for a version a GET would refuse 409; no extra information).
- V7. Auto-prune carried over: a version withheld for a copyright match is pruned like any other after 20 later sends (`circlesend.ts` prune statement, "a withheld version is pruned like any other"), the open `blocklist` flag then has no body to open; the trim path was fixed in round 44, the send path was not.
- V8. Admin `basis=copyright` (`circleadmin.ts` `COPYRIGHT_MATCH_SQL`, third clause) opens a bank when ANY recorded hash of ANY version matches an unlifted block, ignoring expiry and the sender's exemption. Admin-only, audited; looser than the send-time rule. A version release also clears a coexisting student-data hold/flag on the same version (no per-reason release).
- V9. Retention: only the per-address HMAC (HKDF purpose `circle-invite-email`, data prefix `circle-invite-email/v1:`, correctly domain-separated) is stored, cron deletes after two days; D1 time-travel/backups keep it longer (plan 8.1). Without the pool secret it cannot be reversed or enumerated.

## Checked and held (no finding)

- Account-exists oracle: same 202 body, same statements (42-2 plus my timing: the mail is a background `send`, no awaited difference), headers equal; no lookup by address. 400/403/404 ordering uniform (non-member 404 before body read; invalid address 400 is before the role check but a non-owner learns nothing).
- Code leakage: code only in the in-memory notice and the mail (`MAIL_MODE=log` refused off localhost); not in audit, activity, invites list (`kind` only), export, outbox, or logs. `kind` cannot be set by `createInvite`. Emailed code joins through the normal join gates; revoked/expired/erased inviter checks hold (42-5).
- Header/body injection: ASCII-only address, name re-cleaned, JSON `to:[addr]` to the provider.
- Hide keys, every viewer read path (head, versions/:n, history, merge, rollback, trim, blobs, heads, activity, export, report, HEAD/304): stripped by share-core or refused; fail closed 409; messages blanked; images only from recorded `image_shas`; non-author editor/viewer/demoted author cannot turn it off (403); send/PATCH races end in `conflict` (compare-and-set on head and `hide_key`).
- Reshuffle averaging (h3): 2,000 reads of 3 five-choice questions, every choice is uniform over positions regardless of which was correct; Matching right column empty with shuffled distractors; no differing field between reads.
- Publishing the viewer's copy: unmodified copy, label-stripped, reversed, and relabelled variants: refused `circle_material` where the text is the same (h1); relabelled-with-keep variants pass, which equals the baseline of editing any text (not a regression). Closed by recording the served hashes under the first sender, not by luck, with the exception noted in B2 (blocks, not D13).
- Migrations: 0111/0112 add defaulted columns; 0113 rebuild copies every row, recreates `circle_holds_at`, no FK/trigger/view references the table, CHECK accepts `copyright` and rejects others (44-9; I re-read the SQL). Fresh DB and populated 0110 both fine. `cron.ts` delete and `publish.ts` `invalid` export change nothing else.
- Copyright check vs student data: the send answer, version 404 text, `pending_review` text and the circle page are identical for both; held budget and admin mail as the public path.

## Nitpicks

- `circles.ts:1356` validates (up to 1 MB, 60,000 decisions) before the role check; any member can make the Worker parse that body and then get 403.
- `circles.ts:996` activity cursor: the audit id is not bound to the circle, so a foreign `pool_audit` id works as a cursor and compares audit row order across circles (ids are random 128-bit, only a member of both circles knows two). Harmless.
- A failed D1 batch inside `emailInvite` does not give back the daily counters/hourly slot (only the "changes != 1" path does).
- The merge/trim/rollback of hidden-key banks use editors' full text as intended; viewers' history lines still show editors' names and counts (not keys).
