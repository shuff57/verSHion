## Variants and limits

### V1. Rotating an email invite does not kill the OLD code atomically against a join already in flight (low)
- `server/worker/src/pool/circles.ts:711-717`: the join's use-taking `UPDATE circle_invites SET uses = uses + 1 WHERE id = ?1 AND revoked_at IS NULL AND expires_at > ?3 AND uses < max_uses AND ...` is keyed on the invite id, not on the code hash looked up at `:660-664`. The role it grants (`code.role`, `:741`) is the one read at lookup. Round 48's rotation (`circlemail.ts:119`) is the first thing that changes `code_hash` and `role` of a live row, and a revoke is safe (it sets `revoked_at`, which the join re-checks), a rotation is not.
- Repro `c56/j1.test.ts`: owner emails an editor invite to nia@, Nia holds the mailed (old) code. A trigger on the `pool_seq` bump that `joinCircle` makes between its lookup and its batch applies what the rotation does (`code_hash = 'ROTATED', role = 'viewer'`). Result: `POST /circles/join {old code}` answers `200 role: editor`, the invite row ends `uses 1, role viewer, code_hash ROTATED`, the member row is `editor`. So the old code redeemed after it was rotated, with the old role; the rotated code the owner just mailed is dead (uses 1).
- Window: a few milliseconds (`capsOf`, `limitOf`, `nextSeq` run between lookup and use), and it needs the holder of the old code to be redeeming at that instant, so low. The harm case is the one rotation exists for: the owner rotates because the first mail went to the wrong role or the code was seen by someone else.
- Fix: bind the looked-up hash into the use-taking UPDATE (`AND code_hash = ?` and `AND role = ?`, or re-read the role in SQL), the same pattern as every other compare-and-set here.

### V2. Per-sender evidence protection is outside the byte bound: N hostile members pin almost the whole circle in a day, and the owner has no remedy but the administrator (low-medium)
- `circlesend.ts:189`: the byte rule (`x.upto > ?5`, a quarter of `circle_bytes`) is applied only to unprotected rows (`x.pc = 0`). Each sender's newest 5 flagged non-head versions in the circle (and newest 2 per bank) are exempt from the count rule too, in both clauses. A sender can raise 5 flags a day per circle, so each hostile editor adds up to 5 versions (about 20 MB at 4 MB) per day that nobody else can displace, and the circle's `circle_bytes` (200 MB) is reached by about 10 accounts in one day (49 would fit in the member cap of 50).
- Repro `c56/e1.test.ts` (scaled: `circle_bytes` 1.15 MB, 6 hostile editors, each sends 5 flagged versions in one bank then one clean version; an honest member with one flagged-then-fixed version first): used 1,134,239 of 1,150,000 bytes, 25 pinned flagged previous versions = 1,130,740 bytes (98 percent; the quarter rule would be 287,500). Hostile editors 4 and 5 then get `413 quota_exceeded`. Owner remedies: `trim` -> `pruned 0, evidence_kept 5`; delete then `purge-now` -> `200 purged_partial, evidence_kept 5`; removing the member frees nothing (protection follows `committer_id`, not membership); bytes used afterwards 1,135,465 (grew). Only `POST /admin/pool/circle-evidence-captured` on the bank freed it (`flags 5`). So the answer to "is the byte cap deadlock-free for an honest owner": no, not without the administrator; the same holds for heads (known, 55b V2), but round 47 at least bounded the previous versions to a quarter.
- Needs: an active takedown or student-data block to match (any one), hostile editors the owner admitted, one alert mail per flag (budgeted). The admin's tool (capture) works and is one call per bank.
- Suggest: apply the byte bound (or a hard per-circle cap of, say, half of `circle_bytes`) to protected rows as well, oldest first; or let an owner's remove + purge-now of a bank whose flags are older than N days (for example 14) take the bodies, keeping the flags' hashes and positions.

### V3. Refused answer-key PATCH cost: bounded now (measured), residual only with many accounts
- `circles.ts:1478-1498`. `c56/h1.test.ts` (3.1 MB bank with letter labels, so every PATCH is `422 labels_need_decision` after a full strip): 60 attempts took 54.2 s (mean 904 ms; this machine, wasm slower than the Worker's), the 61st and later are `429 daily_limit {metric: circle_hide_attempts}` in 2 to 5 ms, `circle_hide_changes` stayed 0. So one account holds the heavy slot for at most about 30 to 55 s a day, once; the pre-checks (role, same setting, malformed or out-of-range decision, 429) are D1 reads and a JSON parse of at most 1 MB, none of them a strip.
- 40 PATCHes in parallel from one account plus a victim public publish: victim answered `201` in 78 ms, all 40 `422`. Requests of one account are serialised, so the victim is never queued behind more than one of them. To starve other publishers for a minute you need as many accounts as the queue wait allows (the 20 s queue / about 0.5 s a strip = roughly 40 approved accounts bursting at once, each with a circle and a big bank), after which each is out of attempts for the day. Max sustained share of the shared slot per account: 30 to 55 s a day (0.03 to 0.06 percent). I consider B1 of 55b closed.
- Honest-use edge: 60 attempts is 20 banks a day at three steps each (decisions refused, order acks refused, ok); a teacher hiding keys on a department's 25 banks in one sitting is locked out for the day with a plain message. Product, not security.
- `circles.ts:1496`: any `503` thrown from `hideOn` refunds the attempt, including the one the reservation (`hold()`) raises after the strip (55b V8: could not be triggered without memory contention; unchanged).

### V4. Evidence can still be laundered past the flag cap (known limit, now with a cap entry)
`circle_send_flags` is 5 a day per account per circle. The 6th and later matching version of the day is withheld, gets no flag and is not pinned (`PINNED_EVIDENCE_SQL` needs a flag), so the sender or owner can trim it away at once; only the bank's `cap` flag entry (`version`, `actions`, `student_data`) and `circle_qkeys` hashes remain (`c55/a1` re-run and `c56/u1`). A hostile sender burns the 5 flags on junk matching versions (a single matching question), then sends the real infringing text as the 6th: the administrator's case file holds 5 junk versions and the entry. Nothing is readable by members meanwhile (verified), so it is an evidence-quality limit only. The README states it ("not evidence"). Would be cheap to improve: keep the body of a cap-listed version pinned like a flagged one up to a small per-sender number (the byte exposure then is V2's).

### V5. Checked and held (no finding)
- Evidence-captured route (`circleadmin.ts:302-322`): `write: true`, so it goes through the auth package's sudo guard like `circle-hold` (the harness calls handlers directly, so authz itself is the framework's, not tested here); validates `bank_id`, `version` (integer, `"2"` is 400), `note` (10+ chars, 400); unknown bank 404; two audit lines (`pool_audit circle.admin_evidence_captured` plus the admin audit); answers the number of flags changed (`c56/k1`: second capture `flags 0`). It only touches `privacy_text_match` and `blocklist` flags of that bank; a report's pin (`circle_reports`), a hold (`BLOCKING_HOLD_SQL`) and an open report naming a version are separate clauses in trim, the window prune, `evidenceBound` and the purge claim, so capture cannot be used to remove them. The flag stays open (`resolved_at` NULL), so `ONLY_HIDE_FLAGS`, `COPYRIGHT_ONLY_SQL` and hide-off still see it as open; `withheld_at` is never touched: after capture all three of owner, editor, viewer got `404 version_withheld` on the captured version (`k1`). Only the administrator can mark; nothing in a member's path writes `evidence_captured`. It is irreversible (no un-capture) and the administrator can capture without having saved anything: the claim is theirs.
- Purge-now `200 {purged_partial, pending_review, evidence_kept}` (`circles.ts:1857-1890`): what it deletes is every `current`/`previous` version without an uncaptured open flag, with their blob rows; the claim batch re-checks owner, no open report, no blocking hold, `changes() = 1`; undelete is then `409 bank_removed` (`purge_after <= now`); it cannot be used to remove a version a flag or report names, nor a bank under admin removal (`under_moderation`). What stays is the bank row (title, subject, course, grade, history lines, `circle_qkeys` hashes) until the daily purge, so "Everything else in it has been deleted" is true of the text, not of the listing metadata. An owner can still destroy other members' banks immediately after removing them (round 33 power, unchanged) and flagless cap-listed versions (V4).
- `hide_key_changed` and the lost-PATCH `409 conflict {head_version}`: `head_version` is read only after the caller passed the same 404/role gates as the failing request (member of the circle, bank readable at the start); it is the number the history already shows, and `hide_key` is the setting the editor already reads. No information leak found.
- Unblock releasing cap-listed versions (`circleadmin.ts:77-115`, `c56/u1.test.ts`, three runs): (a) student data confirmed after the send: `circle_versions_released 0`, all 7 versions stay withheld, head 404; (b) administrator's manual hold on the bank: `released 0`; (c) plain: all 7 released including the cap-listed 6th and 7th, holds gone, head readable. The sole-reason rule holds because the entry requires `student_data = 0` and every action lifted, the body is re-scanned as a send (`sc.exact/near/copyright`), and the batch re-checks `COPYRIGHT_ONLY_SQL` (privacy block, blocking hold, open report, any non-lifted flag).
- Invite rotation (`circlemail.ts:107-157`): one `UPDATE ... WHERE id AND kind='email' AND revoked_at IS NULL AND uses < max_uses AND expires_at > now` replaces `code_hash`, role, issuer, times in one row, so an old code looked up after the UPDATE is `422` (test 48-9) and a revoked, used or expired invite is not rotated (it answers `409 conflict`); the mailbox count is taken in the same batch and given back if the rotation did not happen; a rotation does not take a plain-code slot. Only V1's window remains. A removed member rotated back in gets a fresh `created_at`, which is the owner re-inviting her by address, as intended.
- Migration 0115: nullable `ADD COLUMN` plus a partial index on `email_key IS NOT NULL`; no existing row changes. Invites that exist before it have no key, so a second invite to the same address makes a second invite (the old behaviour), not an error. 0111, 0113 and 0114 are edited in place with `IF NOT EXISTS`; they are untracked in git (last committed is 0110) so the "applied nowhere" claim holds for the repo; if any D1 database has already run an earlier draft of 0114 (`circle_versions_withheld` on `(circle_id)`), `IF NOT EXISTS` would keep the old, wider index silently: worth a `DROP INDEX IF EXISTS` first (it is only a cost issue, 55b V6).

## Nitpicks

- `circleadmin.ts:92-95`: `block_lifted` is set on the whole `cap` flag when any one of its entries qualifies, although its other entries (another takedown, still active) are not lifted; and the cap flag is never resolved by a release (`c56/u1` plain: all versions released, `cap` flag `resolved_at` NULL, `block_lifted 1`). It stays in the queue as an open item. Resolve it when every entry is released, and set the lifted state per entry.
- `circles.ts:1306` (`patchBank`, since phase B): the `403 circle_role_required` for a member who is neither owner nor author comes before `requireReadable`, so for a bank id the member already knew, `403` against `404` tells whether a held or reported bank still exists (not purged). Needs a known id (128-bit); mention only because 54a asked that held banks look alike to members.
- `purge-now`'s message: "the bank cannot be restored" is said, but the bank still counts as one of the circle's 100 banks until the daily purge after the review.
- `UNBLOCK_RELEASE_MAX` 50 bodies of up to 4 MB in one admin request (about 15 s of CPU here); the response says counts only, not that more are left.
- `trim`'s `evidence_kept` and `purge-now`'s `evidence_kept` fall when the administrator captures: the owner can read the administrator's progress from them. Harmless, noting it.
